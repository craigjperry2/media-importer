Media Importer 🎬

Onboarding & Architecture Overview

System Overview

Media Importer is a production-grade Python CLI tool for incrementally consolidating media files from multiple source directories into a centralized, deduplicated "store". It leverages cryptographic hashing (Blake2b) to ensure integrity, an SQLite catalog to index files and cache hashes, and an atomic, fail-safe execution engine for reliable operations.

Component Architecture

models.py

Contains domain models using standard @dataclass. Defines exactly two core data concepts: domain entities (Blob, FileObservation) and operations (Action subclasses like CopyFileAction).

catalog.py

Manages the SQLite database connection. Contains strict, explicit schemas for blobs (the centralized file records) and source_files (where each file originally came from). Employs WAL (Write-Ahead Logging) for concurrent read scaling.

planner.py

The pure-functional core of the application. It receives a FileObservation, checks database state, and determines exactly what Actions should be taken. It modifies no state itself.

executor.py

The effectful engine. It executes a list of Actions generated by the planner. It ensures atomic file copying (writing to .tmp and replacing) and wraps database mutations within a transaction.

scanner.py & hashing.py

Responsible for filesystem crawling (omitting symlinks) and calculating Blake2b file hashes. Fast, independent, and stateless.

cli.py

Provides the command-line interface. Orchestrates batched pipeline execution to limit memory consumption (_SCAN_BATCH_BYTES) while maintaining UI progress reports.

Code Review & Findings

A comprehensive analysis of the existing codebase. Below are prioritized findings and suggested improvements.

Architecture Pattern: Pure/Impure Separation

The separation between planner.py (pure functions, returning value objects) and executor.py (side-effect management) is excellent. It allows for exhaustive unit testing of logic without mocking filesystems or databases.

IO Bottleneck: Hashing Chunk Size Warning

In hashing.py, the chunk size used for reading files during hashing is relatively small (8KB). Modern SSDs and operating systems perform significantly better with larger buffer sizes (e.g., 1MB or 64KB). 

def calculate_hash(file_path: Path, - chunk_size: int = 8192) -> str:
def calculate_hash(file_path: Path, + chunk_size: int = 1024 * 1024) -> str:
    hasher = hashlib.blake2b()
    with file_path.open("rb") as f:
        while chunk := f.read(chunk_size):
            hasher.update(chunk)
    return hasher.hexdigest()
Margin Note:
Increasing the buffer size to 1MB will drastically reduce the number of system calls (read()) for large video files, yielding a notable performance boost.

Atomic File System Constraints Warning

In executor.py, atomic file replacement is implemented via writing to a temporary file and using Path.replace(). 

tmp_path = Path(f"{full_store_path}.tmp")
shutil.copy2(action.source_path, tmp_path)
with tmp_path.open("ab") as f:
    os.fsync(f.fileno())
- tmp_path.replace(full_store_path)
+ # tmp_path.replace() is atomic on POSIX, 
+ # assuming both paths reside on the same filesystem.
+ tmp_path.replace(full_store_path)
Margin Note:
Because tmp_path and full_store_path are always in the exact same directory, this pattern is perfectly safe and robust. Good job on adding os.fsync to ensure OS buffers are flushed to disk before renaming.

Database Constraints Info

In catalog.py, the schema includes a UNIQUE constraint on file_path in source_files, but querying uses an unindexed lookup (unless relying on the implicit index created by UNIQUE). 

CREATE TABLE IF NOT EXISTS source_files (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    file_path TEXT UNIQUE, -- Note: SQLite creates an implicit index here
    file_name TEXT,
    ...
Margin Note:
Because file_path is declared as UNIQUE, SQLite automatically creates a covering index. The get_observation(file_path) lookup is already optimal.

Exception Shadowing Critical

In executor.py, a broad Exception block catches everything during a transaction, logs it, but does not re-raise or handle specific transaction-breaking errors explicitly beyond skipping DB commit. 

try:
    self.catalog.execute_in_transaction(...)
    db_committed = True
- except Exception as e:
-     logger.error(f"Failed to update database: {e}")
+ except sqlite3.Error as e:
+     logger.error(f"Database transaction failed: {e}")
+     # The batch fails to commit, but the app can safely continue.
Margin Note:
Broad except Exception: can catch KeyboardInterrupt (if not subclassing BaseException) or other critical application errors (like OOM or NameErrors). It's best practice to catch sqlite3.Error specifically when dealing with database transactions.
