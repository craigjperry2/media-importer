Change report · Rust rewrite · Milestone 4

Garbage collection, made deliberately boring.

This change adds explicit two-run mark-and-sweep garbage collection to Media Importer. The design is conservative: the catalog decides what is live, every deletion candidate is verified before mutation, and uncertainty blocks deletion.

The outcome

From “we can detect garbage” to “we can remove it safely.”

Before this change, imports could leave old blobs unreferenced and audit could report integrity, but there was no supported path for reclaiming those blobs. Milestone 4 closes that loop with a narrow gc operation.

Before

  • import, build-tree, and audit.
  • deleted_at_ms existed but had no complete lifecycle.
  • Audit could count marked candidates, never remove them.
  • Re-importing a marked blob could leave it hidden.
→

After

  • A real and dry-run gc command.
  • Fixed mark, resurrect, sweep, and unchanged classifications.
  • Full integrity preflight before the first mutation.
  • Crash-resumable file-first deletion and atomic resurrection.
The core design choice:

GC prefers a false negative (refuse to delete when anything looks wrong) over a false positive (delete content that might still matter). Findings are therefore blockers, not warnings that GC works around.

Start here

The catalog holds the roots; the CAS holds the bodies.

The easiest way to understand the implementation is to separate durable meaning from stored bytes.

source_files = reachability roots

A blob is live when at least one catalog source record points to it. GC does not inspect whether that original source path still exists on a disk.

blobs = lifecycle state

Each blob row carries identity, logical size, creation time, and the nullable deleted_at_ms mark.

CAS files = immutable content

Files live at canonical hash-derived paths. A CAS file with no valid catalog row is an orphan and is never silently adopted or deleted by GC.

A common misconception:

Removing a file from the original source disk does not make its blob unreachable. Only changing durable catalog references does that. Likewise, a browse-tree symlink is an output view, not a reachability root.

The fixed plan

Four run-start states, exactly four decisions.

GC takes one authoritative snapshot and classifies every valid blob row from that snapshot. It does not reclassify rows after marks begin.

Referenced? Already marked? Action Intuition
Yes No UNCHANGED Normal live content; nothing to do.
Yes Yes RESURRECT A live reference wins; clear the stale deletion mark.
No No MARK Record the first committed transition, but keep the bytes.
No Yes SWEEP It was already marked before this run and remains unreachable.

Why two runs?

Run start

Unreachable, unmarked

The blob is classified once as MARK.

→
Commit 1

Mark becomes durable

The CAS file and catalog row remain. This is the grace boundary.

→
Later invocation

Still unreachable, already marked

Only now can it enter the SWEEP set.

Subtle but important:

The boundary is committed state, not “two exit-code-0 processes.” If a mark commits during an invocation that later exits 1 because another sweep failed, that mark still counts as the earlier transition.

One deep operation

Plan everything. Prove safety. Then mutate.

collect_garbage(config) hides the catalog transaction, CAS traversal, hashing, deletion, accounting, and recovery choreography behind one behavior-level API.

Validate paths

Store, blobs directory, and catalog must already be real, non-symlink objects.

Open catalog

Dry-run uses direct read-only access. Real GC reserves an immediate transaction.

Inspect catalog

Check integrity, foreign keys, schema shape, domain rows, and reachability.

Freeze the plan

Sort marks, resurrections, and sweeps by full validated blob hash.

Walk the CAS

Classify every entry without following symlinks and build a valid membership index.

Reconcile & hash

Compare membership and sizes; fully hash present run-start sweep candidates.

Block or apply

Any finding blocks all mutation. A clean real run stages catalog changes and deletes.

Commit & report

Only durably known catalog actions become completed action lines.

SQLite side

The catalog snapshot stays authoritative for the whole real run.

Purpose-specific open policy

  • Read/write and NOFOLLOW, but never CREATE.
  • Schema version must be exactly 1.
  • Journal mode must already be WAL; GC will not convert it.
  • foreign_keys=ON and synchronous=NORMAL.
  • A short busy timeout; inability to reserve is an operational failure.

Immediate transaction

  • Begins before the authoritative reachability query.
  • Schema version is checked again inside the transaction.
  • The same transaction owns the snapshot and every staged mutation.
  • Each defensive update/delete must affect exactly one row.
SELECT blob identity, size, mark,
       EXISTS(source_files reference) AS referenced
FROM blobs
ORDER BY full_hash;

-- Every mutation repeats its safety predicate:
MARK      only when unmarked AND unreferenced
RESURRECT only when marked   AND referenced
SWEEP     only when marked   AND unreferenced
Why repeat predicates after holding a write reservation?

The reservation should prevent ordinary catalog writers from changing the plan, but the predicates make assumptions executable. A zero-row result is treated as an operational failure rather than silently claiming success.

CAS side

A hash-looking path is not enough evidence to unlink a file.

Each present sweep candidate goes through two identity checks: one while hashing and one immediately before removal.

1

Canonical path

The deletion path is derived only from StoreRoot + BlobHash.

2

No-follow open

The final component opens read-only with platform libc::O_NOFOLLOW.

3

Hash & identity

Stream BLAKE3 and record length, device, and inode from the opened file.

4

Revalidate

Immediately before unlink, require the same type, length, device, and inode.

Durability order for a present candidate

revalidate canonical path
    → unlink CAS file
    → fsync containing shard directory
    → stage defensive catalog delete
    → commit SQLite transaction

Empty shard directories are intentionally retained. GC never chmods a candidate merely to remove it, and it never uses a raw path discovered during traversal as a deletion target.

This narrows races; it does not defeat an adversarial filesystem writer.

A final-component replacement after revalidation or a parent-directory replacement remains outside the guarantee. This is why quiescence is a hard precondition, not just performance advice.

Partial failure semantics

Filesystem and SQLite cannot share one atomic commit.

The implementation uses file-first ordering because leaving a marked catalog row with a missing file is recoverable. Deleting the row first and retaining an untracked file would create an orphan.

Failure pointWhat happens nowWhat the report may claim
Mark/resurrection SQL Stop; drop/roll back transaction. No CAS deletion started. No completed actions.
Revalidation, unlink, or directory sync Stop at that candidate; try to commit earlier catalog work. Only earlier committed actions; physical counters remain separate.
Catalog delete after unlink Stop; file may already be absent; commit earlier work if possible. Failing sweep is not completed. Rerun can recover it.
Final SQLite commit Do not guess whether staged changes became durable. No staged catalog actions as known-complete; retain known unlink progress.

Interrupted sweep recovery

Prior run

File removed

The process stops before its marked catalog row is deleted or committed.

→
Next preflight

Exact exception recognized

Marked + unreachable + canonical file absent is not a missing-blob finding.

→
Recovery

Logical sweep finishes

Sync nearest existing parent, delete row, report state=already-absent.

Accounting stays honest:

bytes_unlinked records successful unlink-plus-directory-sync work in this invocation. bytes_reclaimed counts logical bytes only when the corresponding sweep is known to have committed. Already-absent recovery adds zero to both physical-removal and reclaimed-byte totals.

Cross-command fix

Import now atomically brings marked content back to life.

GC resurrection handles a marked row that is already referenced at run start. Import resurrection prevents a successful re-import from creating that stale state in the first place.

This also restores build-tree visibility, because materialization reads only blobs whose deleted_at_ms is null.

User-facing contract

The CLI distinguishes clean completion, blocked safety, and incomplete mutation.

media-importer gc \
  --store STORE_ROOT \
  [--db DB_PATH] \
  [--dry-run] \
  [--chunk-size BYTES]

Exit 0 · Complete

Clean no-op, marks, resurrections, sweeps, mixed actions, or a clean dry-run.

Exit 1 · Operational/incomplete

Invalid paths/configuration, busy SQLite, mutation failure, or failed commit.

Exit 2 · Blocked

Preflight finished and found one or more integrity problems. No app/CAS mutation.

MARK       <64-char-hash> bytes=42
RESURRECT  <64-char-hash>
SWEEP      <64-char-hash> bytes=84
SWEEP      <64-char-hash> bytes=84 state=already-absent

# Dry-run prefixes the same structured plan:
WOULD_MARK / WOULD_RESURRECT / WOULD_SWEEP

Actions are ordered by kind (MARK, RESURRECT, SWEEP) and then by full hash. Blocked runs print findings, not planned action lines. Incomplete runs print only actions known to have committed.

Evidence

The tests focus on outcomes, not private choreography.

Tiny real stores and real SQLite catalogs exercise the command boundary. A narrow injected store mutator covers the mutation failure that is difficult to reproduce reliably with the host filesystem.

  • First run marks; second run sweeps without a time delay.
  • Repeated dry-runs produce the same plan and preserve durable bytes.
  • Prior-mark candidates hash correctly across multiple chunks.
  • All new marks share one injected clock value.
  • GC and import both resurrect referenced content.
  • Re-import restores build-tree visibility.
  • Orphans and candidate hash mismatches block all mutation.
  • Same-size corruption in a non-candidate is not rehashed by GC.
  • Interrupted missing-file sweeps finalize with zero reclaimed bytes.
  • Real GC rejects non-WAL catalogs without converting them.
  • Injected second deletion failure stops later work and commits earlier work.
  • A later invocation completes the remaining marked candidate.

What this does not claim

The change is safe within a deliberately narrow operating envelope.

Hard precondition

The selected store and catalog must stay quiescent from validation until command return. Do not run import, another GC, or external catalog/CAS writers concurrently.

Logical, not physical, bytes

“Bytes reclaimed” sums cataloged logical sizes. ZFS compression, snapshots, deduplication, sparse allocation, reflinks, and hard links can change physical space recovery.

Deliberately deferred

  • Catalog-backed cross-command run locking.
  • Source-record pruning based on current source disks.
  • Orphan repair, adoption, quarantine, or deletion.
  • Time-based grace periods and retention configuration.
  • Relationship-aware reachability roots.
  • Directory-descriptor-relative unlinking.
  • Globally atomic filesystem/SQLite mutation.
  • JSON output, progress dashboards, and parallel hashing.
Practical runbook:

Keep the store quiet, run gc --dry-run, resolve every finding, then run real GC. After collection, rerun build-tree if you maintain a materialized browse view, because old links may now be stale.

1. What makes a blob reachable in Milestone 4?

Answer: Reachability is durable catalog state. Source-disk existence and browse-tree links are not roots.

2. Why can a newly marked blob not be swept in the same invocation?

Answer: The fixed snapshot creates the two-transition boundary. There is no time-based grace in this milestone.

3. A run commits a mark, later hits a sweep error, and exits 1. Is that blob eligible to sweep next invocation if still unreachable?

Answer: Per-blob committed transitions, not process exit status, define the boundary.

4. Which statement about gc --dry-run is correct?

Answer: Dry-run is a complete read-only safety preflight, not a cheap estimate.

5. What happens when preflight finds a valid orphan CAS blob?

Answer: Orphans lack a catalog lifecycle and therefore block GC; repair is a future workflow.

6. Which is the correct order for deleting a present candidate?

Answer: File-first ordering makes interruption recoverable; directory sync strengthens deletion durability.

7. What identity is checked immediately before unlink?

Answer: The path is canonical and the final file must still match the opened file's type, size, device, and inode.

8. When is a missing canonical CAS file treated as an interrupted sweep instead of a finding?

Answer: The exception is deliberately narrow. Missing live or newly markable blobs remain blocking findings.

9. What does re-importing content do to a matching marked blob?

Answer: Import resurrection makes catalog existence, live state, and the source reference atomic.

10. What does “Bytes reclaimed” mean?

Answer: Physical recovery can differ because of compression, snapshots, deduplication, sparse files, reflinks, and hard links.

11. Why must the store and catalog remain quiescent during GC?

Answer: The transaction protects catalog state, not the separate filesystem. Milestone 4 has no global run lock.

12. A final SQLite commit returns an error after one file was unlinked and synced. What can GC safely report?

Answer: Failed commit durability is ambiguous. The report stays conservative while preserving directly observed unlink/sync progress.
