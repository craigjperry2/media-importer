Milestone 1 Architecture

Directory import into the content-addressed store

The first Rust slice keeps one command narrow and complete: scan a source directory, hash regular files, install immutable BLAKE3-addressed blobs, and record source observations in SQLite. 

media-importer import \
  --store <STORE_ROOT> \
  --source <SOURCE_DIRECTORY> \
  [--db <DB_PATH>] \
  [--dry-run] \
  [--chunk-size <BYTES>]

Module Boundaries

Milestone 1 uses a functional core with side effects at the module edges. The CLI validates and dispatches, ingest coordinates behavior-level interfaces, and low-level filesystem or SQLite details stay inside store and catalog.

Responsibility Map

CLI

Owns argument parsing, command-level validation, dispatch to ingest::import_source, tracing setup, and concise stdout summaries.

Paths

Owns canonicalization, source/store/database overlap rejection, source-relative path serialization, staging paths, and CAS sharding paths.

Scanner

Uses walkdir to collect sorted regular-file candidates, including hidden files while ignoring symlinked files and directories.

Ingest

Coordinates scanner, store, catalog, clock, and report counters through behavior-level APIs. It aborts on the first error.

Store

Reads each source once in chunks, hashes with BLAKE3, writes a staging file, installs with hard-link-then-unlink, and makes blobs read-only.

Catalog

Hides SQLite connection handling, PRAGMAs, schema versioning, migrations, and the per-file transaction that records imported files.

CAS Layout

Stores blobs under blobs/<hex[0..2]>/<hex[2..4]>/<hash> plus a sibling staging directory and default catalog.sqlite.

Reporting

Stable command output is a human summary. Internal diagnostics use tracing; progress bars and JSON output are deferred.

Real Import Workflow

  1. Validate paths and command config Canonicalize the source root, validate or derive store and database paths, reject source/store/database overlap, and construct typed identities.
  2. Prepare durable edges Create the store root and known children if needed, purge stale staging contents, and open or initialize the SQLite catalog.
  3. Scan deterministically Collect regular-file candidates from the source directory and sort by slash-normalized source-relative path.
  4. Ingest each candidate Read the file in configured chunks, hash while writing to staging, verify size and mtime stability, and compute the final CAS path from the hash.
  1. Install or reuse blob Hard-link the staged file into the CAS if absent. If present, verify size, make sure permissions are read-only, and remove the staged file.
  2. Commit catalog observation In one per-file transaction, upsert blobs, upsert source_files, preserve first-seen data, and increment seen_count.
  3. Update import report Count files seen, created/reused blobs, inserted/updated source records, bytes seen, and bytes written.
  4. Stop on first failure Earlier successful files remain imported. There is no milestone 1 rollback; snapshots and future audit/GC handle recovery concerns.

Dry-Run Contract

Dry-run is read-only against durable state. It may validate paths, scan source files, hash source data, inspect existing CAS blobs, read an existing catalog without mutation, and produce the same shape of report using "would" language.

It must not create the store root, blobs, staging, database files, WAL or SHM files, parent directories, migrations, blob files, or catalog records. Missing catalog means "empty catalog" for planning purposes.

Catalog Schema V1

blobs

Content identity and lifecycle state for each unique BLAKE3 hash.

  • hashTEXT primary key
  • size_bytesINTEGER
  • created_at_msINTEGER
  • deleted_at_msnullable INTEGER

source_files

Source path observations pointing many source paths at one blob.

  • source_rootcanonical text
  • relative_pathslash-normalized
  • blob_hashFK to blobs
  • seen_countidempotency counter

Guardrails For The Slice

No placeholder commands

Only import is exposed. build-tree, gc, and audit remain future work.

No ORM

SQLite is accessed through raw SQL behind catalog APIs, with visible schema and migration behavior.

No broad concurrency yet

Workers, single-writer batching, managed checkpoints, progress dashboards, and metadata-skip optimization are deferred.
