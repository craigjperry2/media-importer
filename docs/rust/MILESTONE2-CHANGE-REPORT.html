The outcome

One new command turns durable storage truth into a disposable view.

Before this milestone, imported media existed safely but inconveniently: blob filenames were 64-character BLAKE3 hashes arranged for machine access. The new build-tree command reads the live catalog and creates a separate tree whose names resemble the original source paths.

The central idea

The catalog and CAS are authoritative. The browse tree is derived state. It can be rebuilt, reconciled, or discarded without changing the stored media or catalog.

Input

SQLite catalog

Supplies live source-relative paths, full blob hashes, and expected sizes.

Proof

Content-addressed store

Supplies the actual regular files that each desired link must target.

Output

Browse tree

Contains relative symlinks with readable names plus short hash suffixes.

Context and intuition

The CAS solves identity; the browse tree solves navigation.

Content-addressed storage names a blob by what its bytes are. That is excellent for deduplication and integrity, but poor for a person looking for Movies/Clashing Name.mp4. Milestone 2 deliberately keeps those concerns separate.

store/ catalog.sqlite blobs/ ab/ c1/ abc123...full-64-character-hash browse/ Movies/ Clashing Name_abc123.mp4 -> ../../store/blobs/ab/c1/abc123...full-64-character-hash

Why not rename blobs?

The full hash is the blob's stable identity. Human names can collide, change, or appear under multiple source roots. Renaming blobs would weaken the CAS model.

Why symlinks?

Symlinks add a cheap presentation layer without duplicating media bytes. Multiple readable names can point to one deduplicated blob.

Why a hash suffix?

The source-relative path alone is not globally unique across source roots. A short hash prefix distinguishes different content while keeping names readable.

Why rebuild instead of update during import?

Import remains focused on durable ingestion. Presentation is reconciled offline, which keeps source scanning, CAS mutation, catalog writes, and view generation independently understandable.

Mental model

Read truth, prove targets, compare state, then reconcile.

The implementation is easiest to understand as five transformations. Only the final one mutates the browse tree.

1. Validate Canonicalize roots, reject overlap, check hash-digit range.
2. Project Read live catalog rows and derive desired output paths.
3. Prove Require each CAS target to be a regular file with the cataloged size.
4. Diff Classify links, blockers, stale owned links, and directories.
5. Apply Create or replace desired links, clean stale links, prune empty dirs.

Dry-run follows the same first four stages and returns the same plan counters, but it skips stage five. This is important: dry-run is not a second, approximate implementation.

Command surface

The CLI added one narrow, complete command.

media-importer build-tree \
  --store <STORE_ROOT> \
  --browse-tree <BROWSE_TREE_ROOT> \
  [--db <DB_PATH>] \
  [--dry-run] \
  [--hash-digits <N>]
Argument Behavior Reason
--store Required; must already be a real directory with a real blobs/. Materialization consumes an existing store and never initializes one.
--browse-tree Required; may exist as a real directory or be one missing final component. The command may create the browse root, but not arbitrary parent paths.
--db Defaults to <store>/catalog.sqlite. An explicit catalog may live in the store, but never inside the browse tree.
--dry-run Runs validation and planning, reports "would" counters, mutates nothing. Users can inspect reconciliation before filesystem changes.
--hash-digits Defaults to 6; accepts 1 through 64 inclusive. Controls presentation-name disambiguation without changing blob identity.

Milestone scope stayed narrow

This change exposed build-tree beside import. It did not expose placeholder gc, audit, or --json behavior.

Stable reporting contract

BuildTreeReport carries desired, created, unchanged, replaced, stale removed, directory created, and directory pruned counts. The CLI renders real and dry-run wording from the same fields.

Path safety

Path validation is part of the security boundary.

This command creates and deletes filesystem entries, so path spelling cannot be treated as cosmetic. The implementation canonicalizes trusted roots and validates persisted relative paths again before joining them.

1

Store root

StoreRoot::validate_existing_for_build_tree uses symlink_metadata, rejects a symlink root, requires a directory, canonicalizes it, and requires blobs/ to be a real directory.

2

Browse root

An existing root must be a real directory. For a missing root, its real existing parent is canonicalized and the intended final component is appended.

3

Overlap

Store-inside-browse and browse-inside-store are both rejected. An explicit DB path inside the browse tree is rejected as well.

4

Catalog paths

Persisted paths must be non-empty, slash-normalized relative UTF-8 paths. Absolute paths, ., .., empty components, backslashes, drive-like prefixes, and UNC-like forms are rejected.

Why validate catalog paths again?

Milestone 1 normally writes safe relative paths, but persisted data is a trust boundary. A manually edited or damaged catalog must not turn browse_root.join(relative_path) into traversal outside the generated tree.

Read-only catalog projection

The catalog API returns typed desired-state ingredients, not raw rows.

Materialization gained a dedicated read-only opener. It does not migrate or create a database and requires schema version exactly 1. 

SELECT
    source_files.relative_path,
    source_files.blob_hash,
    blobs.size_bytes
FROM source_files
JOIN blobs ON blobs.hash = source_files.blob_hash
WHERE blobs.deleted_at_ms IS NULL
GROUP BY source_files.relative_path, source_files.blob_hash
ORDER BY source_files.relative_path, source_files.blob_hash;

Live only

Rows whose blob has a non-null deleted_at_ms are excluded from the desired browse tree.

Deliberate dedupe

Grouping by relative path and full blob hash collapses duplicate observations that would produce the same desired link.

Deterministic order

Ordering by relative path and hash makes planning and diagnostics stable across runs.

Rows are decoded into LiveMaterializationEntry, which contains a validated SourceRelativePath, validated BlobHash, and unsigned expected size. SQL remains in the catalog boundary through a colocated .sql file.

Presentation naming

Only the final filename changes; its full blob identity does not.

Catalog relative path Hash begins Default browse path
Movies/Clashing Name.mp4 abc123... Movies/Clashing Name_abc123.mp4
Movies/README abc123... Movies/README_abc123
Movies/.env abc123... Movies/.env_abc123
archive.tar.gz abc123... archive.tar_abc123.gz

Filename intuition

If the filename has a non-empty stem before its final extension, the suffix is inserted before that extension. Dotfiles and extensionless names receive the suffix at the end. Multiple-dot names preserve only the final extension as the extension.

Collision handling

A BTreeMap is keyed by the transformed output path. If two different catalog entries collapse to the same path because their selected hash prefixes match, planning fails before mutation and recommends rebuilding with more digits, such as --hash-digits 12.

Symlink targets are relative

The target text is calculated from each link's parent directory to the absolute CAS blob path. This makes the generated tree independent of the current working directory and avoids storing an absolute target when a canonical relative target is available.

Generated versus user-managed state

Ownership is inferred from where a symlink points.

The browse tree may contain user files or user-managed symlinks. The tool therefore needs a conservative rule for what it is allowed to replace or remove.

An owned symlink is under the browse root and its target text, interpreted relative to the symlink parent and normalized lexically, points inside the configured store's blobs/ tree.

Existing entry At desired path? Action
Owned symlink with exact expected target text Yes Unchanged
Owned symlink with absolute or non-canonical target text Yes Replace
Owned symlink no longer desired No Remove as stale
User-managed symlink pointing outside blobs/ No Leave alone
User-managed symlink pointing outside blobs/ Yes Block and fail
Non-symlink file Yes Block and fail
Non-symlink file No Leave alone

Ownership is lexical and does not require the target to exist. That lets the command remove dangling stale links that still clearly point into this store. It also means ownership checks do not resolve symlinks or traverse the filesystem target.

Functional core, imperative shell

Known errors are found before the first mutation.

build_tree first creates a complete Plan. A real run applies it; a dry-run returns its report. The plan contains desired links, stale owned links, directories to create, directories to prune, and all counters.

  1. Open the catalog read-only. Missing, uninitialized, or newer schemas fail.
  2. Load and validate live entries. Persisted paths and hashes become validated types.
  3. Derive desired outputs. Transform final filenames and compute relative target text.
  4. Validate every CAS target. It must be a regular file with the cataloged size.
  5. Detect output collisions. No ambiguous short-hash name can enter the plan.
  6. Walk existing browse state. Classify owned links and desired-path blockers.
  7. Compute reconciliation. Count create, unchanged, replace, and stale removal actions.
  8. Validate parent directories. Existing symlinked or non-directory parents block.
  9. Simulate pruning. Count empty directories after stale links and child dirs disappear.
  10. Apply only for a real run. Dry-run stops here with the completed report.

Why desired links come first

During apply, desired links are created or replaced before stale cleanup. A link that remains desired is never deliberately removed first.

Why replacement uses rename

A replacement target is first created as a temporary symlink in the same directory, then renamed over the old owned link. This avoids a normal replacement window with no link at all.

No rollback

Planning catches known problems before mutation, but unexpected apply-time I/O failures abort immediately without rolling back earlier actions. Stale cleanup only starts after all desired link operations succeed. A later rerun can reconcile partial generated state.

Mutation boundaries

The command mutates only the generated presentation tree.

May create

Browse directories

The final browse root, when missing, and real child directories required by desired links.

May replace

Owned symlinks

Only links whose normalized target points into the configured blobs/ tree.

May remove

Stale owned links

Plus empty child directories after cleanup. The browse root itself is never pruned.

Never mutate

Catalog

SQLite is opened read-only and no migrations are run.

Never mutate

CAS blobs

Blob files are validated as link targets, not changed.

Never overwrite

User entries

Non-symlinks and externally pointing symlinks are preserved or treated as blockers.

Directory pruning is bottom-up

Candidate ancestors of stale owned links are considered deepest first. The planner accounts for already-prunable child directories, while the apply phase uses remove_dir, which succeeds only for an actually empty directory.

The deep interface

Callers ask for build_tree(config) -> Result<BuildTreeReport>. They do not perform SQL, construct blob paths, walk the filesystem, or choreograph cleanup themselves.

Boundaries and implications

What this milestone deliberately does not promise.

No repair

Missing or size-mismatched CAS blobs cause failure. Build-tree does not restore, rehash, or rewrite content.

No rollback transaction

Filesystem apply is ordered defensively but is not transactional. Unexpected I/O failure may leave partially applied generated state.

No content rehash

CAS target validation checks entry type and cataloged size. Full content integrity verification belongs to a later audit capability.

No Windows target

The command creates Unix symlinks and the project explicitly targets Linux and macOS.

No metadata filtering

All live catalog entries are projected. There is no MIME or media-extension selection in this milestone.

No catalog mutation

Materialization does not record runs, ownership, or generated paths in SQLite. Ownership is inferred from symlink targets each time.

Useful invariants to carry forward

  • The CAS and catalog are durable truth; presentation trees are rebuildable.
  • Persisted relative paths are revalidated at every filesystem join boundary.
  • Dry-run and real execution share planning logic.
  • Only owned symlinks may be replaced or deleted.
  • Known blockers and corrupt targets are detected before mutation.
  • Raw SQL remains owned by the catalog module.

Pass: 10 / 12
1. Which state is authoritative after Milestone 2?

The browse tree is disposable generated state. Catalog rows describe desired identity and CAS files hold the durable bytes.

2. What does --dry-run skip?

Dry-run uses the real planner, including validation and diffing, then returns the plan report without applying it.

3. How is archive.tar.gz named with prefix abc123?

Only the final extension is preserved as the extension. The suffix is inserted before .gz.

4. What makes a symlink "owned" by this command?

Ownership is target-based, not name-based or process-memory-based. That allows stale links from previous hash-digit settings to be recognized.

5. An existing desired symlink resolves to the right blob but stores an absolute target. What happens?

"Unchanged" requires exact expected target text. An owned absolute or non-canonical target is replaced.

6. Which catalog rows become desired links?

The SQL includes all live entries, deliberately dedupes by relative path and full hash, and performs no MIME or extension filtering.

7. What does CAS target validation prove before linking?

Milestone 2 checks entry type and size. Full content hashing is not part of build-tree.

8. A user-managed symlink points outside the CAS and occupies a desired output path. What happens?

The command never replaces a symlink it does not own. At a desired path, that means it must fail rather than lose user state.

9. Why can a short hash-prefix collision not be resolved by picking one row?

The presentation identity is ambiguous at that prefix length. The safe response is to fail before mutation and ask for more hash digits.

10. In what order does the real apply phase reconcile links?

Desired links are applied before stale cleanup. Pruning happens last and never removes the browse root.

11. What schema behavior does the materialization catalog opener use?

Build-tree neither creates nor migrates the catalog. Missing, uninitialized, and newer schemas fail clearly.

12. What happens if an unexpected I/O failure occurs halfway through apply?

Apply is not transactional. It aborts on the first error. Stale cleanup does not begin unless all desired-link operations succeeded.
