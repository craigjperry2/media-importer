Before and after

Before

Import could create catalog and CAS state, and build-tree could materialize a browse view. There was no command that independently proved the durable catalog still matched stored bytes.

After

Operators can run a non-mutating, full-content audit and distinguish a clean store, discovered integrity damage, and an audit that could not finish.

Context & intuition

Think of the catalog as a ledger and the CAS as the vault.

Neither side is enough by itself. The catalog says what should exist and records its expected identity and size. The CAS contains the actual bytes under paths derived from their BLAKE3 hashes. Audit asks whether the ledger and vault agree—and whether each is internally sound.

SQLite catalog · the ledger

  • Blob hash and expected byte size
  • Source-file observations
  • Deletion marker used as a GC candidate
  • Schema, constraints, and foreign keys
Compare
both ways

CAS filesystem · the vault

  • Canonical path derived from hash
  • Regular-file type and metadata length
  • Actual streamed byte count
  • Actual BLAKE3 digest
The central invariant:

A healthy blob has one valid catalog identity, one canonical regular CAS file, matching sizes, and content whose BLAKE3 digest equals both the catalog hash and filename.

CLI behavior

The command is deliberately narrow.

media-importer audit \
  --store <STORE_ROOT> \
  [--db <DB_PATH>] \
  [--chunk-size <BYTES>]

--store

Required. The store and its blobs directory must already exist as real directories—not symlinks.

--db

Optional. Defaults to STORE_ROOT/catalog.sqlite; an explicit catalog may live inside or outside the store.

--chunk-size

Optional and non-zero. It controls bounded streaming memory, not the amount of content verified.

Exit status is part of the API

Exit Meaning Output channel Example
0 · clean Audit completed and found no integrity problem. Summary on stdout All catalog blobs exist and hash correctly.
1 · operational Configuration or an operational failure prevented a complete audit. Error report on stderr Missing catalog, unreadable root, unsupported schema.
2 · findings Audit completed, but one or more integrity findings were discovered. Findings and summary on stdout Missing blob, orphan, hash mismatch.
Why exit 2 is not an exception.

Finding damaged or inconsistent data is a successful execution of the audit operation. The report is returned as normal domain data, rendered fully, and only then mapped to exit 2. Exit 1 is reserved for “we could not finish inspecting.”

Execution model

One deterministic pass, with side effects kept at the edges.

1. Validate inputs Real store, blobs root, catalog, non-zero chunk
2. Snapshot catalog Read-only transaction, checks, raw row decoding
3. Classify CAS Raw-byte order, no symlink traversal, strict layout
4. Reconcile & hash Union of identities; each canonical file once
5. Sort & render Stable findings, exact counters, exit selection

The orchestration lives behind the deep operation audit_store(AuditConfig) -> Result<AuditReport>. CLI code does not choreograph SQL or filesystem traversal; catalog code does not inspect CAS paths.

Why hash after traversal instead of during traversal?

Completing classification first produces deterministic reconciliation work and keeps filesystem discovery separate from content verification. It also makes it straightforward to hash each valid identity at most once, even when the file is both a catalog match and a CAS entry.

SQLite side

The database is opened read-only, but “read-only” has WAL nuance.

SQLite may hold committed data in a non-empty write-ahead log. Opening the main database as immutable while such a WAL exists could ignore those committed frames. Milestone 3 therefore uses a hybrid policy.

No non-empty WAL

Build a correctly percent-encoded SQLite URI using mode=ro&immutable=1. The quiescence precondition makes the immutable assertion safe and prevents sidecar creation.

Non-empty WAL exists

Require real, readable WAL and SHM sidecars and open with mode=ro without immutable mode, allowing SQLite to observe committed WAL frames.

Non-empty WAL without usable SHM is exit 1.

Audit refuses to inspect stale main-database state, does not create the missing sidecar, and tells the operator to cleanly close or checkpoint with a writer before retrying.

Catalog verification has three layers

01

SQLite engine integrity

Run PRAGMA integrity_check and PRAGMA foreign_key_check. The single integrity_check row ok is explicitly ignored.

02

Semantic schema shape

Validate ordered columns, declared types, nullability, PK roles, FK shape, indexes, uniqueness, required CHECK constraints, and unexpected user objects.

03

Domain row values

Decode through raw SQLite values so wrong storage classes become findings rather than panics or premature query failures.

Rows are validated, not blindly deserialized

Table Important checks Invalid-row result
blobs 64 lowercase hex hash; non-negative size; integer creation timestamp; null or integer deletion timestamp. INVALID_BLOB_ROW; row still counts in catalog total.
source_files Non-empty root; portable relative path; valid referenced hash; matching size; positive seen count; ordered timestamps. INVALID_SOURCE_ROW; later rows are still inspected.

SQL used by the application was extracted to colocated catalog/sql/*.sql files and loaded with include_str!. A Rust source-policy test prevents application SQL literals from returning unnoticed.

Filesystem side

Only one path shape is a valid blob.

STORE_ROOT/ └── blobs/ └── 01/ first two lowercase hex digits └── 23/ next two lowercase hex digits └── 0123…(64 hex)…cdef full matching BLAKE3 hash

A valid CAS blob is a regular file at exactly that depth. Empty valid shard directories are allowed. Everything else is either an invalid CAS entry or a local I/O finding.

Strict classification

  • Lowercase two-character hex shards only
  • Exactly 64 lowercase hex characters in filename
  • Shard prefix must match filename
  • No shallow files or over-deep content
  • No symlinks or special files

Safe traversal identity

  • Directory entries sorted by raw OsStr bytes
  • Non-UTF-8 and control bytes rendered as \xNN
  • Malformed real directories are traversed
  • Symlinked directories are never followed
  • Final blob open uses no-follow behavior on Unix
Why raw bytes matter.

to_string_lossy() can collapse different invalid byte sequences into the same replacement character. Raw-byte sorting and escaping keep finding identities collision-resistant and deterministic on Linux and macOS.

Bidirectional truth

Reconciliation is a set comparison plus content proof.

Size has three witnesses

For a cataloged file, audit compares the catalog size, metadata length from the safely opened file, and streamed byte count. A size mismatch does not skip hashing: full hashing can reveal independent corruption in the same run.

Deleted blobs are still expected

A non-null deleted_at_ms marks a blob as a GC candidate. It is not an instruction for audit to ignore or expect absence. Audit counts it once and verifies its CAS file exactly like a live blob.

Safety properties

Read-only is treated as a behavior to prove.

No durable mutation

No store creation, migrations, repair, deletion, checkpoint, staging cleanup, chmod, or catalog lock acquisition.

Race-resistant final open

Classify with symlink metadata, open the final blob with no-follow behavior, then hash the already-open file and inspect its opened metadata.

Bounded content memory

One file is streamed at a time through an explicitly reserved chunk buffer. Content memory is O(chunk size).

Resource and overflow discipline

  • Potentially large indexes, finding lists, directory-entry lists, schema results, reconciliation keys, and hash buffers use try_reserve.
  • Allocation failure becomes an operational error instead of an uncontrolled assumption.
  • Blob counts, hashed-file counts, GC candidates, and streamed byte counts use checked arithmetic.
  • Malformed SQLite presentation is bounded so damaged values cannot force huge diagnostic output.
Quiescence remains a correctness precondition.

SQLite can provide a consistent database snapshot, but the catalog and CAS cannot be snapshotted atomically together. A concurrent import could transiently resemble an orphan or missing blob. Milestone 3 documents this rather than enforcing a cross-resource lock.

What changed later in Milestone 4?

Reusable finding identity, stable sorting, CAS traversal, and no-follow blob open were extracted into shared integrity and store facilities for garbage collection. The current audit.rs is therefore shorter than the original Milestone 3 implementation, but its external contract remains the same.

Review-driven corrections

The implementation was tightened substantially during review.

Initial vertical slice

CLI, config, catalog inspection, CAS traversal, reconciliation, hashing, report rendering, and exit status mapping were connected end to end.

SQL ownership corrected

Audit SQL literals were moved from catalog.rs into colocated .sql files. A Rust integration policy test now scans production sources and fails cargo test—and therefore prek—if application SQL is inlined again.

README consolidated

Obsolete scaffold and Milestone 1 language was removed. Commands, audit cost, quiescence, report-only behavior, deleted-blob semantics, and exits were presented as one coherent current document.

WAL and immutable handling completed

The simplistic read-only open became a percent-encoded SQLite URI policy that distinguishes no-WAL immutable access from existing WAL-backed snapshots.

Schema validation became semantic

Object-name checks were expanded to column order/types/nullability/PKs, FK shape, required indexes, unique identity, CHECK constraints, and extra user objects.

Filesystem identity and resources hardened

Lossy path conversion was removed from stable identity, sorting moved to raw bytes, classification became a pure function, allocations gained fallible reservation, and counters gained checked arithmetic.

Adversarial coverage expanded

Tests grew from the initial happy-path and basic failure cases to WAL, schema impostor, malformed-value, immutability, deleted-blob, orphan corruption, non-UTF-8, layout, ordering, and multi-chunk scenarios.

Verification strategy

Tests exercise observable contracts with real tiny stores.

The suite favors CLI integration tests backed by real temporary directories and SQLite catalogs, plus focused unit tests for pure CAS classification and raw path rendering.

Clean and outcome tests

Help surface, exact counters, default and explicit DB paths, exit 0/1/2, non-zero chunk behavior, and unchanged import/build-tree outcomes.

Catalog adversaries

WAL visibility, missing SHM, schema impostors, wrong FK and CHECK constraints, foreign-key violations, malformed storage classes, and invalid domain values.

CAS adversaries

Missing blobs, size-plus-hash corruption, deleted blobs, orphans, malformed depths and shards, symlinks, empty shards, ordering, and non-UTF-8 names.

Deliberate boundaries

What Milestone 3 does not do.

No mutation or repair

  • No deletion, quarantine, chmod, move, or repair
  • No automatic marking of unreferenced blobs
  • No migration or managed checkpoint
  • No staging cleanup

No expanded inspection surface

  • No browse-tree verification
  • No source filesystem reinspection
  • No quick or metadata-only audit mode
  • No JSON, workers, progress bars, or parallel hashing
Why the narrow scope is valuable.

Milestone 3 establishes trustworthy classification and reporting without combining it with destructive policy. That separation made the later mark-and-sweep garbage collection milestone safer to build and easier to review.

1. What does audit exit status 2 mean?

Exit 2 is a completed domain outcome. Operational or configuration failures use exit 1.

2. Why does the audit reconcile catalog and CAS in both directions?

Catalog → CAS detects missing or non-regular expected objects. CAS → catalog detects canonical files with no row.

3. When is immutable=1 used?

Immutable mode could ignore committed WAL frames. It is safe in the no-WAL branch under the quiescence precondition.

4. A canonical CAS file has no catalog row and its content hash is wrong. What should be reported?

These are distinct facts: the file is unindexed and its bytes do not match its canonical identity.

5. How is a blob with non-null deleted_at_ms treated?

Logical deletion is not physical absence. Audit reports, counts, and verifies; it does not sweep.

6. Why are filesystem names sorted and identified by raw bytes?

Raw bytes preserve distinct non-UTF-8 names. Presentation escapes unsafe bytes as \xNN.

7. If catalog size differs from filesystem metadata, does audit skip hashing?

Milestone 3 has no quick mode. Full hashing is intentionally performed despite a size mismatch.

8. Which entry is a valid CAS blob?

Validity requires exact depth, lowercase hex, matching shard prefixes, full hash filename, and a regular file.

9. Why does catalog row decoding use raw SQLite values?

A damaged non-STRICT database may contain text where an integer is expected. The audit records that row-level problem and continues where safe.

10. What is the content-memory complexity of hashing?

Metadata indexes scale with catalog and CAS entries, but blob content is never buffered wholesale.

11. Why must the store remain quiescent during audit?

A concurrent import can temporarily make valid in-progress state look like an orphan or missing blob.

12. Where should application SQL live?

Raw SQL belongs to the catalog boundary and remains separately reviewable in colocated SQL files.
